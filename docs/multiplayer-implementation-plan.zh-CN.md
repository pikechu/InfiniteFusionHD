## 本次核实的项目基础

- `Game.ini` 指向 `Data/Scripts.rxdata`。本地可信 Marshal 解包确认其中只有 Main 加载器，按每层“文件排序、再子目录排序”读取 `Data/Scripts`，不是打包后的全部游戏代码。
- 因此新增 `Data/Scripts/054_Multiplayer/*.rb` 会在 UI、战斗、AddOns 之后，`999_Main` 之前加载；不覆盖 rxdata。源码加载使用的 eval 是**本地代码加载**，网络协议不使用它。
- `999_Main/999_Main.rb` 在 `mainFunctionDebug` 中运行插件、`Mods/*.rb`，再初始化数据和游戏。Mods 可以覆盖战斗规则，不能仅核对游戏版本。
- 当前工作区已有 Android、HTTP、暂停菜单、多存档等修改。本次采用新目录和 prepend 扩展；不重置这些文件，不将已有修改算作本次成果。
- 原 OnlineWondertrade 是不完整客户端，不具备可信交换状态机。现有普通 Wondertrade 仍为离线玩法。
- 战斗代码和动画均有直接 rand 调用；录像类的存在不证明全部改版可确定回放。

## 技术选择与职责

采用 Python 3 标准库 `ThreadingHTTPServer`、`sqlite3`，游戏端 Ruby + JSON + 后台网络 worker/主线程帧泵轮询。适合 Windows 本机验证，无需 Node 包、Redis 或独立数据库。默认仅绑定 127.0.0.1。公开部署需要单独安全和容量评审，当前不执行。

| 层 | 职责 | 不承诺的能力 |
| --- | --- | --- |
| 游戏客户端 | UI、队伍白名单快照、临时 Pokemon、输入、显示、身份凭据持久保存 | 不修改主队伍，不生成可交易奖励 |
| 房主计算端 | 唯一运行现有 PokeBattle_Battle，收取锁定指令，发布公开状态与结果 | 无防作弊保证；无任意时点引擎迁移 |
| 客机 | 发出自己的选招/换人指令，014使用原生PokeBattle_Scene播放白名单动画并应用权威状态 | 不运行第二套伤害/随机计算；素材不全可显式降级 |
| HTTP 服务 | 身份认证、房间、兼容检查、幂等、锁定、断线额度、唯一结算、展示投影 | 不验证 Ruby 战斗计算是否作弊 |
| SQLite | 身份、业务操作、房间、战斗/回合/结算、展示版本 | 不把客户端上报当作可信经济资产 |

HTTP 网络等待继续 `Graphics.update`、`Input.update`，不按每帧请求网络。最终采用015的Ruby core Socket/非阻塞IO，连接、读、写共用一个deadline，响应头16KiB、body沿用有界JSON上限，严格解析Content-Length/chunked/EOF，拒绝重定向和不明确帧边界。mkxp缺少socket.rb便捷包装时使用已原生验证的底层非阻塞connect。**禁止联机调用原生HTTPLite**：源码和无游戏最小用例确认其释放GVL后创建Ruby对象，长期并发会损坏堆。worker不异步kill，主线程超时后保留inflight保护至IO自然关闭；DNS仍受系统resolver时限影响，等待期间不冻结画面，也不无限追加线程。联机scope关闭旧素材下载并ensure恢复单机设置；worker存活时暂缓Platform旧HTTP。默认Game没有OpenSSL，HTTPS在写pending前明确拒绝，绝不降为明文；带OpenSSL的独立Ruby使用证书链和主机名验证，不能因此声称默认Game支持公网TLS。Android沿用原有外部adapter，未在本次Windows验收。

请求超时后保留request_id，先查询操作再决定是否补发同一编号。身份/服务器切换还核查pending、道馆报告、休闲交换/池以及可信本地escrow；只能恢复所属原身份，不能把交易重放到新账号。只读回放下载不占用业务journal，避免损坏文件锁死以后交易；旧版误存的只读journal只作安全迁移。

## 身份、兼容、快照和协议

服务创建不可预测的 player_id、Bearer token、独立恢复码。数据库只保存凭据散列；恢复轮换 token。客户端按服务器 URL 分区身份，并支持独立测试 profile。昵称、好友码为公开数据；恢复码和 token 不进入名片、房间、日志。恢复码必须由用户单独安全备份。

协议为 `/v1`、UTF-8 JSON。每次业务修改包含 `request_id`，服务按玩家和编号记录动作及结果；编号相同但内容不同必须拒绝。字段校验包含类型、允许键、大小、整数范围、枚举；不接受 Ruby 对象、脚本、类名和任意资源路径。认证使用 Authorization，不放 URL。

兼容信息包含 protocol、game、rules、data、mods 摘要。数据摘要覆盖实际参与计算的脚本/编译数据，新增、删除、修改均检查。标准房间固定规则包，不允许运行时本地选项暗中改变规则。**相同 Mods 哈希不证明安全或兼容**：当前标准规则直接拒绝任何 Ruby Mod 和非空插件归档，只允许本次实际测试的无 Mod 构建。尚未适配的复杂形态/三重融合/未知字段必须在准备前阻止；红/蓝宝珠及究极奈克洛 Z 在当前适配中禁用，Mega 关闭，其他动态形态仍需独立扩大覆盖。

参赛快照版本 1：物种/融合 ID、等级、性别、性格、特性（含双特性）、招式及 PP、IV/EV、携带物、个体身份和外观受支持字段。从白名单字段创建全新 Pokemon；不使用现有 load_json/eval 导入。候选为三到六只，选择恰好三只，顺序冻结，等级标准化至 50，治愈仅作用于副本。网络格式不等同于将来交换保留字段格式。

公开队伍预览只含物种/融合组成。选择顺序、招式、道具、IV/EV、未触发特性不进房间响应。房主可通过受认证战斗端点获得全数据。正常客机只拿自己的私有队伍与对手已公开场上资料。房主修改客户端可观察隐藏资料；文档和 UI 不作保密/可信排位承诺。

## 房间与战斗状态机

房间：等待/配置 → 双方准备 → 游戏中 → 结算/等待 → 关闭。服务器事务检查容量、成员权限、房主权限和当前状态。换队、改规则、移除成员清除准备。重复 start 返回原 battle_id；新一轮准备后再战产生新编号。房主等待时可关闭，战斗中不能通过踢人改变结果。

战斗有独立 battle_id，每个需要输入的阶段有递增操作编号；forced switch 不与正常回合共用易歧义编号。动作是 move(move_index,target)、switch(party_index)、forfeit。第一份动作只公开“已提交”；第二份到达后事务锁定，只有房主获取双动作。锁定前允许撤回，锁定后迟到/撤回拒绝。引擎再次验证 PP、目标、束缚/换人和补位合法性。

房主结算一次，服务按 battle_id + 操作编号保存结果。引擎唯一运行，因此客机动画速度与随机数不参与计算；不能把双方相同种子当作同步手段。随机轨迹仅作审计，需要覆盖所有战斗随机入口后才可称完整录像。公开状态包含场上 HP、PP（只给所有者）、异常、天气/场地、登场变化、战斗文本和最终结果。终局唯一，不发主线奖励。

**需求具体修订**：首个技术闭环允许客机菜单式战报，先验证真实远端控制与权威一致结果；完整双端动画仍是第一版验收门槛。没有完整引擎恢复快照时，房主丢失内存或服务重启后应异常结束，不能声称恢复任意回合，更不能补交单方本地胜利。

## 故障、计时与持久化

| 故障 | 规则 |
| --- | --- |
| 网络响应丢失 | 用原 request_id 查询操作；已成功则采用原结果；查不到再发同一编号 |
| 重复/迟到动作 | 已锁定不能改写；内容冲突返回明确错误 |
| 非房主断线 | 当前阶段暂停，累计扣减 60 秒；重连不重置额度 |
| 房主断线 | 额度内仅同一内存引擎继续；无法恢复则异常中断 |
| 双方均失联 | 异常结束，无奖励 |
| 选招超时 | 60 秒；补位 30 秒；默认合法动作；连续三次操作超时认输 |
| 动画/结算 | 操作倒计时暂停；两端 acknowledge 后开启下一阶段 |
| 状态不一致 | 暂停，查询服务器；不能修复则异常结束 |
| 服务重启 | 已完成业务记录保留；未完实时战斗标异常结束，不复活旧房间 |
| 不兼容 | 连接/准备时拒绝并列出差异，不尝试运行未知规则 |

SQLite用事务、唯一键和WAL，落地表包括identities、operations、rooms、battles、showcases、gyms、gym_versions、gym_challenges、gym_favorites、rewards、trades、trade_receipts、pool_deposits、hosted_assets、asset_locks、halls、dungeons、replays、cards。业务document保存成员、逐阶段快照、随机轨迹与唯一结算；rewards主键(owner,scope)、receipt主键(transaction_id,owner)、asset_locks主键asset_id保障一次性业务。副本战斗最终六只team_states和result在同一事务落库，advance只需battle_id，不能在服务重启后依赖房主补交猜测状态。`digest`是权威收据，客机验证展示的权威HP等，不独立重算战斗。备份应停止服务或使用SQLite backup API，不能仅复制活动WAL主文件；测试全部使用独立库。

本地存档备份和导入可复制精灵。休闲交易流水只解决正常重试和故障恢复，**UUID 不证明来源，不能阻止主动回滚复制**。服务器托管个体才以服务器权威归属为准；两类区服和 UI 标签隔离。

## 阶段与验收门槛

1. 技术验证：服务/真实引擎/独立身份、远端招式与换人、完整结算和再战、原队伍保护；自动化与 GUI 验收分开记录。
2. 第一版：设置身份恢复、两人房间、展示、六选三标准单打；两台机器、不同速度、断线/迟到/版本不符、终局一致全部通过后才标完成。
3. 第二版：依次 Boss、道馆、好友交换；每项专用状态机和中断恢复通过后再开放入口。
4. 第三版：租借→交换池→大厅；每项竞态、断线、资产隔离和实机验收通过。
5. 后续：托管箱、固定副本、分享回放独立交付，不以按钮和空接口算完成。

本轮按用户继续开发第二版的指令推进后续模块：人工/跨机发布验收保持独立待验，同时完成不受环境限制的实现和本机真实游戏验证。没有将第一版跨机门槛倒填为通过，各阶段代码完成与发布完成分列。

原生GVL错误已经最小复现并以安全Socket替换，默认Game完整长流程通过；客机原生动画已落地。剩余验收风险是全部招式/动态形态组合、人工菜单、跨机网络以及缺失本地立绘；房主内存迁移仍不支持。采用可复现探针、受支持范围白名单及不兼容即阻止，不能把已测几个场次外推成全部引擎机制通过。

## 第二版以后已落地的具体协议

- Boss：槽0/2分别属两人，敌人槽1。服务冻结boss_id/version/difficulty；每个阶段只接受所属槽动作、合法目标或补位。非房主额度耗尽时保留已锁动作，由AI补齐以后动作；重连下一指令阶段回收控制。客户端失联只脱离观看，不中止仍运行的房主/AI。队伍全灭可持续旁观，包含副本下一节点初始已全灭。普通Boss奖章按玩家/战斗唯一；副本节点禁止领Boss奖。
- 道馆：publish只新增不可变version；challenge持有完整版本快照，馆主离线/更新/关闭不改变已有挑战。客户端真AI战斗、独立隔离，无主线奖励。challenge报告持久保存，响应丢失通过operations收回原challenge，进程丢失则上报abnormal，不能补写胜利。奖章按道馆/账号唯一。
- 休闲交换：TradeCodec是独立于对战Snapshot的严格保留格式，详见字段表。存档内escrow先锁原个体，profile日志用于恢复；服务双确认事务生成transaction_id，客户端一次原子存档替换并写应用标记后才ack。交换和池共享escrow互斥，同一存档/服务器/身份核验；已保存未ack的进程硬退出可重读只补ack。确认前不支持字段/外观素材即拒绝。
- 租借：安装可信游戏导出目录，服务随机抽取/保存十二只完整候选，ABBAAB每步有draft_id+pick_index，迟到请求不消耗下一个同玩家的回合。实际使用好友单打适配，不复制到主存档。并非靠种子生成两份队伍。
- 交换池和托管：投递在waiting/matched/withdrawn/expired/claimed间事务流转；同区非本人匹配，每账号仅一份waiting，24h过期取回。托管starter只能从服务器安装目录领取一次，asset属性不可由客户端覆盖，所有者变更及锁由同一事务维护。托管模式仅缓存显示，从本地导入不能变成可信asset。
- 大厅：固定social-lobby-v1/20×15专用RGSS场景，最多4人、位置序号、方向/表情及会话邀请；0.35秒节流后台轮询，与不可重试的经济操作分离。接受邀请创建真实room/trade，已打开邀请ID持久记忆；地图不符退菜单，返回原世界。
- 固定副本：3普通战→各人一次固定恢复→最终Boss。创建时冻结两人/敌人，六只HP/PP/异常/道具跨节点；状态只能取已提交战斗全队权威快照。24h到期；进行中绑定房间和成员，不可绕过route开平行普通战。未提交中断允许一次恢复到pre-state，正常战败直接失败；双方放弃投票。只有最终通关可领run_id奖章。
- 分享回放：已结束支持玩法保存初始队伍、逐阶段锁定指令、房主pbRandom记录、白名单动画、完整公开权威帧及终局。双方主动同意后公开，分享码访问每次重查公开与同意状态，不能靠旧operation缓存绕过下架。播放器校验版本/所有帧及最终结果后在隔离场景播放，不改存档。

**回放设计修订**：采用记录权威状态的状态录像，保证受支持记录播放到相同终局，而不调用原单机BattleRecord再次执行伤害。原引擎/素材含直接rand，pbRandom轨迹并不覆盖全部随机入口；因此不声称任意Mod、底层随机或旧版本可确定重算。房主计算仍属休闲信任边界，录像不是防作弊证明。
