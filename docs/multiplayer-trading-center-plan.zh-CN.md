# PokeMMO 风格交易中心方案

日期：2026-10-22。状态：设计基线。精灵交易、道具与体验、托管在线角色均已有实现；使用方法、运行时条件及验收边界见 [交易中心说明](multiplayer-trading-center.zh-CN.md)。下文的「当前」描述方案制定时的基线，最终行为以实现说明和测试证据为准。

2026-10-23 更新：本文原先后置的交易功能现已扩展实现，包括成交历史、收藏搜索和提醒、资产邮件、部分成交、拍卖、求购、代练、租赁与抵押借贷。规则及验收状态见 [交易扩展说明](multiplayer-trading-expansion.zh-CN.md)；下文保留原设计顺序。

## 1. 建议结论

在现有联机功能上新增统一的「交易中心」，包含面对面交易、全球交易市场（GTL）、我的出售、待领取和交易记录。保留现有好友休闲交换、奇迹交换池和服务器托管收藏箱，通过统一入口串联。

产品体验参考 PokeMMO：玩家可以直接协商交换，也可以把资产按一口价挂到市场，其他玩家搜索后购买，卖家离线也能成交。针对 KIF 增加融合头部／身体、双特性、自定义闪光外观等筛选和详情。

推荐分两层推进：先用现有服务器托管资产做出完整交易闭环，再接入主线在线精灵、道具和金币。后一层需要补齐在线资产权威管理，不能把现有云存档同步当作已经完成了在线经济。

需要明确体验边界：当前托管收藏箱中的精灵只能收藏、展示和交换，不能进入主队伍培养。因此第一阶段属于可验证的交易中心封测版本；要实现「买一只精灵，放进主队伍继续冒险」的目标，必须交付第 12 节的主线接入阶段。

本文中的槽位、费用、时限等均为本项目建议默认值，不代表 PokeMMO 的实际配置。

## 3. PokeMMO 和 OpenMMO 分别参考什么

### 3.1 PokeMMO：参考玩家流程

官方 GTL 说明包含全服挂牌、搜索和高级搜索、菜单／宝可梦中心电脑入口，以及购买后的邮件或库存交付；其买卖权限与首个地区四枚徽章关联，上架费用会提前显示。[来源：PokeMMO GTL 官方说明](https://support.pokemmo.com/knowledgebase/article/the-gtl-system)

本项目借鉴：

- 面对面协商和离线挂牌并存。
- 搜索、查看完整个体、核对价格、确认购买构成连续流程。
- 上架前明确显示手续费、数量、总价和到期时间。
- 收纳空间不足时保留服务器待领取资产。
- 直接交易采用「锁定清单 → 最终确认」两步操作；这是本项目拟定的交互规则。

首版采用一口价市场，竞价拍卖、求购单、代练服务、租赁和借贷后置。玩家可通过直接交易自行议价。

### 3.2 OpenMMO：参考协议分层和资产建模

已核对本机 `D:/others/OpenMMO` 与公开仓库，二者提交均为 `7277550f0ac9995dcae5a773f13715475370069e`。该版本有上架、购买确认、取消、搜索、我的挂牌和交易日志等协议结构；但核对服务端处理器和服务目录，未发现这些协议对应的完整交易市场业务闭环。部分协议字段仍带未知语义，不能按文件存在就视为功能已经实现。

| 可以参考 | 本项目如何采用 |

| 搜索、我的挂牌、购买、取消、记录分别建模 | 拆分对应服务职责与接口 |
| 物种、性别、性格、等级、IV、闪光、价格等筛选维度 | 结合 KIF 融合与外观扩展 |

## 4. 模块范围与入口

| 模块 | 玩家能做什么 | 首版范围 |
| --- | --- | --- |
| 面对面交易 | 邀请附近玩家或输入好友码，双方协商资产与金额 | 托管精灵、多只组合、联机币；道具后续加入 |
| 全球市场 | 搜索精灵、查看详情、一口价购买 | 托管精灵市场 |
| 我的出售 | 选择资产、填写价格、上架、撤单、查看成交 | 离线保持挂牌 |
| 待领取 | 查看购入、撤单、到期资产及恢复结果 | 资产留在服务器，不以邮件附件复制 |
| 交易记录 | 查看成交时间、对手、金额、手续费和流水号 | 本人记录，支持断线后查询 |
| 原有交换玩法 | 好友休闲交换、奇迹交换池、托管收藏箱 | 继续保留来源提示与恢复入口 |

推荐入口：

1. 在线暂停菜单增加「交易中心」。
2. 联机菜单原「交换与托管收藏」进入统一交易首页。
3. 宝可梦中心 PC 增加「全球交易市场」；与暂停菜单使用相同账号库存。
4. 地图增加「附近玩家 → 选择玩家 → 发起交易」，桌面右键与手机触控作为同一操作的不同输入方式。

市场按服务器隔离；不同服务器、来源区和不兼容资产版本不能跨区交易。钱包按在线账号管理，同账号多个存档槽不重复发放余额。历史恢复码身份保留旧功能，新市场买卖资格要求已绑定注册账号，不能通过新建临时身份领取市场额度。

## 5. 界面与搜索设计

### 5.1 交易首页

顶部显示联机币余额和待领取数量，正文提供「全球市场／出售／我的挂牌／面对面交易／待领取／记录」。旧休闲交换和奇迹交换池位于「其他交换」入口。

桌面采用列表加详情布局；窄屏采用列表、详情、确认三个页面。筛选和翻页保留当前位置，避免购买后从第一页重新找。

### 5.2 市场列表与详情

精灵列表显示：立绘缩略图、物种或融合组成、等级、闪光标记、性格、关键 IV、售价和剩余时间。详情展示原训练师、双特性、全部 IV／EV、招式、携带物、外观参数摘要及交易限制。

培养参数显示资产的实际数据，不能被本机「全 31 IV」「无 EV」等单机选项覆盖。闪光预览使用受支持素材编号及颜色参数，不执行卖家脚本或加载任意文件路径。首版缺少对应素材时显示缺失占位并阻止购买确认，安装素材后重新预览，避免买家根据不准确的替代图成交。

| 搜索组 | 条件 |
| --- | --- |
| 常用 | 名称／图鉴号、纯种／融合、等级区间、价格区间、闪光、性格 |
| 对战 | 性别、特性／第二特性、六项 IV 下限、31 IV 项数；0 攻／0 速用精确值条件 |
| KIF | 头部物种、身体物种、任一部位包含指定物种；三者语义分别明确 |
| 道具阶段 | 道具名称、分类、数量、单价；明确区分单价与整单总价 |

按价格、最新上架、即将到期、等级、IV 总和排序，所有排序增加挂牌 ID 作为稳定次序。每页建议 20 条，服务器限制筛选数量并使用游标分页。列表允许短暂缓存；购买始终重新校验挂牌、价格和归属。

## 6. 面对面交易流程

建议每方最多 6 只精灵、8 种道具和一笔金额；道具功能在对应库存阶段启用。允许单向赠送，拒绝双方均为空的交易。交易对象始终使用认证身份和好友码确认，昵称只用于展示。

1. 发起邀请，对方接受后建立会话；邀请建议 30 秒失效，可以拒绝、屏蔽或关闭邀请。
2. 双方编辑清单。服务器校验所有权并锁定精灵；道具数量和金额作相应预留，可用余额立即扣除预留额。
3. 双方分别点击「锁定清单」。任何清单变更都会递增报价版本，并取消双方锁定和最终确认。
4. 双方锁定后，展示完整最终清单及双方净变化，建议等待 3 秒后允许最终确认，计时依据服务端时间。
5. 双方最终确认相同版本、内容哈希和金额，服务器在同一事务中完成全部转移。
6. 双方读取同一成交编号，刷新库存和钱包；客户端未收到结果时查询原会话，不重新交易。

提交前允许取消；已提交只能恢复结果。未提交断线会话保留短暂恢复时间，超时取消并释放预留；最终确认与取消竞态由数据库事务决定。新会话建议空闲 3 分钟、最长 10 分钟自动结束，心跳不无限延长；旧休闲交换维持原协议和到期规则。

首版托管资产直接进入接收方收藏箱，容量不依赖本地主队伍。主线接入后，还必须在提交时校验队伍可用性、库存容量及对应角色状态；不能交换后才发现主线已无可用精灵。

## 7. 全球市场的业务规则

### 7.1 上架

从服务器可用库存选择资产，不能上传客户端快照创建挂牌。每只精灵一单；道具阶段允许同种堆叠，首版道具按整单购买，部分成交后置。

上架确认页同时显示售价、数量、总价、上架费、预计到账和期限。服务器在一次事务中校验卖家资格、槽位、资产归属和余额，然后锁定资产、收取费用、生成挂牌及操作回执。失败则全部不生效。

| 参数 | 建议默认值 |
| --- | --- |
| 活跃挂牌上限 | 每账号 10 单，可配置 |
| 挂牌期限 | 7 天，采用服务器时间 |
| 价格 | 正整数；服务端校验单价、数量乘积及钱包上下限 |
| 上架费 | 整单售价的 2%，向上取整，最低 100、最高 25,000 联机币 |
| 成交费 | 首版 0，减少买卖双方理解成本 |
| 撤单／到期 | 不退上架费；资产进入待领取 |
| 改价 | 撤单后重新上架，并重新收取费用 |

例如精灵售价 50,000：上架扣费 1,000，成交后卖家钱包增加 50,000，净收入为 49,000。费用规则在上架时冻结，运营修改不追溯既有挂牌。数值仅供封测评估，正式配置随经济来源一并确定。

### 7.2 购买

1. 买家打开详情，服务端返回挂牌版本、完整资产摘要和价格。
2. 买家核对并确认；提交挂牌 ID、预期版本、预期总价和唯一操作编号。
3. 服务端重新检查资格、未过期、仍在售、买卖双方不同、资产锁、兼容版本及买家余额；检查卖家收款后不超过余额上限。
4. 同一事务内扣买家款、加卖家款、转移唯一资产归属、将资产放入买家交付容器、把挂牌置为已售、写双方流水及回执。
5. 买家在待领取页收纳到托管收藏箱；卖家款项已经到账，通知和查看记录不再次发钱。

两名买家同时购买同一只精灵时只能一人成功。另一人收到「已售出」且余额不变。超时提示「正在核实交易结果」，客户端查询原操作编号；不能自动生成新购买请求。

### 7.3 撤单和到期

挂牌状态只允许从在售进入已售、已取消或已过期之一。撤单、购买和到期处理使用同一事务规则，只能产生一个结果。定时任务负责批量清理，购买请求本身也检查到期时间，不依赖清理任务准时运行。

撤单／到期时，把挂牌锁原子替换成交付锁，资产仍归卖家，生成唯一退回记录。卖家领取后才重新成为可用库存；不能通过删除锁的方式让一只精灵同时处于挂牌和库存中。

## 8. 钱包、资产来源与待领取

### 8.1 资产来源分开处理

| 来源 | 可以做什么 | 边界 |
| --- | --- | --- |
| `local_casual` 本地休闲精灵 | 现有好友交换和休闲奇迹池 | 可被导入或存档回滚复制，不进入联机币市场 |
| `server_managed` 托管精灵 | 新面对面交易、GTL、托管池和展示 | 当前归属与属性由服务器决定 |
| 未来在线主线资产 | 主队伍、PC、背包及经济流通 | 完成来源和变更验证后再接入 |

现有携带物作为精灵快照的一部分随个体转移，首版收藏箱不能独立取出。接入托管道具和主线后，携带物必须改为库存关联或等价的单一归属记录，禁止既算精灵附件又算背包数量。

### 8.2 货币与供给

建议首版使用独立的服务器「联机币」，不自动等额兑换本地金币，不从云存档中的金钱字段充值。所有余额使用整数，转账、手续费、发放和回收均写复式流水，系统发行和手续费回收也有对应账户。

封测可为白名单账号一次性发放测试余额和多样化目录资产，额度绑定账号、带唯一发放事件；测试经济不能直接继承为正式服经济。仅靠现有每账号固定 starter，会导致商品同质化和小号刷取问题，不能当作正式供给方案。

正式经济需要一并设计可信发行渠道和消耗：例如经过审核的服务器活动发放、服务器认可的任务奖励／掉落，以及上架费和后续托管培养消费。现有客户端上报的胜利、在线时长、徽章和本地道具数量不直接兑换联机币。可信产出未完成前，市场保持封测或限定活动范围，不能声称已经具备完整 PokeMMO 式主线经济。

四徽章可以作为未来的玩法门槛，但必须基于服务端认可的角色进度；首版测试资格由服务端名单管理。禁止以客户端上传的徽章数量代替资格校验。

### 8.3 待领取的含义

交易中心提供系统交付收件箱，不先实现玩家任意发资产邮件。每个交付记录指向已经存在的服务器资产或成交事件，不保存一份可无限生成精灵的附件模板。

- 购买成功时，资产归属已经变为买家，但处于不可交易的待收纳容器。
- 「领取」只把该资产从交付容器移到收藏箱，重复操作不生成资产。
- 撤单、到期也使用同样的交付流程，归属仍为原卖家。
- 卖家货款即时进钱包，收件箱只显示通知。
- 未领取资产不因通知过期删除；断线、换设备后可继续查询。
- 已领取旧记录只展示历史结果，不把后来已转手的资产重新发给旧领取者。

## 9. 服务端结构与数据设计

### 9.1 延用当前技术栈

继续使用 Ruby 客户端、Python 服务和 SQLite，市场与原托管交换、交换池使用同一资产归属与锁。首版按现有单写服务实例运行；搜索只读路径需单独评估，避免每次翻页都占用当前通用请求入口的写事务。

业务可拆为交易服务、市场服务、钱包台账和交付服务四部分，仍在同一进程／数据库事务内协调。内存缓存和通知不能决定余额或所有权。后续只有在写锁等待、查询延迟和数据量证明需要时，再迁移 PostgreSQL；不为参考 OpenMMO 而重写为 Kotlin。

### 9.2 核心数据

| 数据 | 主要内容／约束 |
| --- | --- |
| 现有 `hosted_assets` | 不可变资产 ID、当前所有者、权威属性；扩展版本、容器及交易资格 |
| 现有 `asset_locks` | 一个资产最多一把锁；统一识别好友交换、交换池、挂牌和交付引用 |
| `wallet_accounts` | 账号、币种、可用与冻结金额、版本；余额和冻结金额不得为负 |
| `ledger_transactions` / `ledger_entries` | 一次业务一组借贷分录，按币种借贷合计平衡；发放事件唯一 |
| `market_listings` | 卖家、资产引用、数量、冻结价格／费用规则、状态、版本、到期时间 |
| `market_orders` | 买家、卖家、挂牌、唯一成交 ID、金额、结果；整单挂牌最多一个成交订单 |
| `exchange_sessions` / `exchange_offers` | 双方、资产集合、金额预留、版本、锁定与最终确认、期限 |
| `item_balances` / `item_holds` | 道具阶段增加，分别记录实际数量和各操作占用数量 |
| `deliveries` | 所有者、原事件、资产引用、状态；原事件与交付项唯一 |
| `trade_events` | 上架、撤回、过期、成交、领取等审计事件，不记录登录凭据 |
| 现有 `operations` | 认证身份加请求 ID 唯一，保存指纹与原结果 |

资产没有第二套「市场副本」。查询字段可建立受控投影和索引，但修改时回到原资产核对版本与归属。收藏展示转让后的撤销沿用现有 `transfer_asset` 规则。

托管锁的刷新与清理要增加 `market:`、`delivery:` 等类型，并同时覆盖原好友交换／池逻辑。过期清理只能根据所属业务终态释放锁，不能只因锁创建时间较久就删除。

钱包、资产、挂牌、成交、交付和幂等回执必须在同一提交边界。旧本地交换仍依赖安全存档恢复，新市场结算不依赖买卖任一方客户端在线。

### 9.3 拟定接口

以下仅为接口规划，不是已有功能。保留原 `/v1/trades` 处理旧会话，新多资产交易使用独立资源，避免改变旧客户端的恢复语义。

| 接口 | 用途 |
| --- | --- |
| `GET /v1/market/config` | 可用功能、资格、费用、限额、资产版本 |
| `GET /v1/wallet` | 余额、冻结金额及钱包版本 |
| `GET /v1/market/listings`、`/{id}` | 条件搜索、游标分页、挂牌详情 |
| `GET /v1/market/my-listings` | 本人挂牌及历史状态 |
| `POST /v1/market/listings` | 上架已有服务器资产 |
| `POST /v1/market/listings/{id}/buy`、`/cancel` | 带版本的购买／撤单 |
| `POST /v1/exchanges`、`/{id}/accept` | 邀请并建立新交易会话 |
| `GET /v1/exchanges/{id}` | 恢复当前状态和本人结果 |
| `POST /v1/exchanges/{id}/offer`、`/lock`、`/confirm`、`/cancel` | 编辑、锁定、双确认、取消 |
| `GET /v1/deliveries`、`POST /v1/deliveries/{id}/claim` | 系统交付与收纳 |
| `GET /v1/trading/history` | 当前账号交易记录 |
| 现有 `GET /v1/operations/{request_id}` | 不确定响应恢复 |

所有经济写入保留唯一 `request_id`；同 ID、同参数返回原结果，同 ID、不同参数拒绝。买卖资格、所有者、总价和状态由服务端推导；不能接受客户端指定卖家收款账号、资产新所有者或「交易成功」标记。

## 10. 状态与异常处理

挂牌业务状态：在售 → 已售／已取消／已过期。交付状态独立为待收纳 → 已收纳；客户端是否看过通知不影响成交。

直接交易状态：邀请中 → 协商中 → 双方锁定 → 已提交。每方最终确认记录附在相同报价版本上；提交前可取消／过期，提交后的客户端确认仅作展示同步，不再次触发转账。

| 场景 | 要求 |
| --- | --- |
| 同一精灵同时上架、报价、投递池 | 同一资产锁决定唯一可用操作 |
| 同一笔钱同时用于购买和直接交易 | 钱包可用额扣除全部预留，事务内再次校验 |
| 购买与撤单／到期同时发生 | 只有一个终态；失败方不发生扣款或资产转移 |
| 双方锁定后更换精灵或金额 | 旧锁定和确认全部失效，重新查看和确认 |
| 扣款过程抛出异常 | 整组钱包、归属、订单、交付和回执回滚 |
| 服务器提交后响应丢失 | 用原请求编号查询，返回同一订单与结果 |
| 领取成功后客户端崩溃 | 新进程读取已收纳记录，不再复制资产 |
| 读取历史回执时资产已转手 | 显示历史，不覆盖当前归属 |
| 服务重启／到期任务重复运行 | 业务记录和预留持久化，重复执行不重复退款或退回 |
| 账号切换或云存档旧版本恢复 | 新账号不能操作旧账号资产；云存档不能覆盖钱包与市场归属 |

运营需要按流水查询、暂停新交易、停止异常账号的新增操作、查看锁与对账差异。涉及错误修复时使用可审计的补偿事件；不能直接改余额、删除流水或为已成交商品重新生成副本。市场暂停期间保留历史查询和恢复能力，终态交付按独立开关控制。

生产延用 `synchronous=FULL` 和完整一致性备份；这不代替备份恢复演练。恢复数据库备份会回退市场和钱包状态，恢复时必须统一数据版本、令客户端缓存失效并核对回退窗口，不能只还原市场表或用客户端旧回执重造资产。

## 11. 道具和交易频道扩展

第二阶段引入服务器道具库存，按服务端目录明确标记可交易种类。普通消耗品、材料和进化道具可逐项开放；关键道具、剧情绑定物、账号绑定物与未适配邮件类道具禁止。TM／HM 等必须按本项目具体规则评估，不能只照搬其他游戏的分类。

交易频道沿用现有消息管道，扩展独立频道类型与限流。商品分享只发送受控的挂牌编号和展示摘要，点击后重新查询挂牌；自由文本和旧商品卡不授予购买权。首版不依赖聊天成交，仍以直接交易或市场最终确认页为准。

价格历史、收藏搜索和到货提醒后置。价格统计只统计真实成交，过滤自身与明显关联账号刷量；首版不显示缺乏样本支持的「市场估值」。

## 12. 实施顺序与主线接入

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| 0：确定规则 | 页面草图、来源边界、货币、费用、资格、数据迁移设计 | 明确首版是否必须包含主队伍买卖；本文为建议基线 |
| 1：资产和钱包基础 | 扩展统一锁、钱包台账、交付容器、测试资产与额度、迁移和审计 | 资源占用、原子结算、重复请求和重启恢复成立 |
| 2：精灵交易封测 | 精灵 GTL、搜索、上架／购买／撤单、我的挂牌、待领取、记录；多精灵加币直接交易 | 两个真实客户端完成完整链路，未完成旧交易仍能恢复 |
| 3：道具与体验 | 道具台账和市场、组合交易、PC 入口、附近邀请、交易频道、移动端适配 | 物品数量、金额预留和跨端恢复实测通过 |
| 4：在线主线经济 | 在线角色资产、金币来源、捕获／培养／融合／使用／消费验证，主队伍和 PC 接入 | 买入资产可用于冒险，全部变更仍在同一权威账本下 |

如果首版目标就是「现有主线精灵和金币像 PokeMMO 一样直接买卖」，阶段 4 必须前移并成为上线前置，不能在阶段 2 完成时把它标成已交付。

### 主线接入需要补齐的内容

1. 服务端分配稳定的在线角色 ID、资产 ID 和经济版本；存档槽只是角色快照位置，复制或新建槽不产生新的资产和领取额度。
2. 主队伍／PC 展示服务器资产投影；消费、移动、释放、携带道具和交易均核对当前经济版本。云存档恢复不能把旧所有者、旧物品数量或旧余额写回账本。
3. 捕获、孵化、奖励、升级、学招、进化、融合／拆分必须有服务器认可的过程与结果。仅校验数值范围不能证明玩家实际获得过资产；当前房主上报战斗结果也不能直接产出可信经济奖励。
4. 融合必须原子消耗对应组成资产并生成有来源链的新资产；拆分按记录恢复组成，防止两份原料与融合体同时流通。携带物也服从同一资产守恒规则。
5. 交易进化由唯一成交事件触发受控的后续变更，预览要明确；不能让每次客户端重新播放交换动画都再进化或消耗道具。
6. 上架、领取或转让涉及主线时，和在线角色写租约、云存档版本及经济版本协调；过期客户端无法上传旧队伍覆盖已转出的资产，另一设备上线必须先刷新经济投影。
7. 历史本地资产默认保留休闲来源。可以另设一次性、带来源限制的迁移区，但人工审核、UUID、哈希或「首次上传」均不能把来源不明资产变成已验证捕获；不能自动进入可信市场。

这一阶段规模明显大于增加一个市场页面，应按在线经济改造单独拆分任务。若只追求朋友间自由买卖，也可另选标明复制风险的休闲市场；那是不同产品取舍，其资产、币种和搜索结果仍必须与托管市场分区。

## 14. 验收清单

- 两个独立账号完成邀请、改价／改清单、锁定、双确认、资产与金额转移；任一报价变化会取消旧确认。
- 买家购买卖家离线挂牌；双方余额、费用账户、资产归属和订单一致。
- 两名买家抢一单，以及购买／撤单／过期竞态，只产生一个合法结果。
- 相同资产跨市场、好友交易、交换池同时使用被拒绝；同一余额不能被重复预留和消费。
- 在写钱包、转资产、写交付、提交和响应前后分别模拟异常，结果完整提交或完整回滚。
- 提交后断网、客户端硬退出、服务器重启、重复请求和重复领取均能恢复同一结果。
- 历史回执不重发已转手资产；新建存档、恢复旧云存档和换设备不重置钱包或发放额度。
- 普通、双融合、双特性、闪光颜色及受支持立绘能准确预览和保留；不支持扩展有明确原因。
- 原好友休闲交易、托管交易、奇迹交换池和收藏展示回归通过；旧待处理记录仍可恢复。
- 所有权唯一、道具数量非负、冻结额不超余额、按币种台账平衡；新发行与回收均有独立流水。
- Windows 两个真实游戏进程先验收，再分别执行两台设备和 Windows／Android 最终同构建混合验收；接口测试不能代替实机结论。
- 正式经济另验可信产出、角色恢复、融合／拆分和主队伍消费；测试额度与封测数据不得直接进入正式服。

优先完成「选择托管精灵 → 上架 → 另一账号搜索购买 → 钱包结算 → 收纳资产 → 重启恢复」，再扩展多资产协商和道具。以这一完整链路作为交易中心第一项可演示成果。
