**KIF 玩家管理与全服经济统计后台方案（讨论稿）**

日期：2026-10-22。范围：产品、指标口径、数据基础、操作流程、实施分期与验收。本文最初作为讨论方案交付；后续开发范围、完成情况和剩余边界见[后台使用与开发验收](multiplayer-admin-operations.zh-CN.md)。

建议新增独立的 Web「运营管理后台」，覆盖玩家查询、全服统计、经济分析、GM 操作、异常排查和操作审计。游戏客户端继续使用现有联机入口，管理员通过浏览器管理服务器。后台与商城、交易中心共用账号、资产和经济流水。

本文采用以下建议默认值：以单服运营为首期范围；统计默认按 Asia/Shanghai 自然日汇总；现有 Matomo 保留下载与匿名安装活跃统计；本次后台负责登录账号和游戏业务；真实支付报表在支付业务接入后启用。上述内容是规划建议。

**2. 最重要的数据边界：什么才是“全服总金币”**

当前主线金币、背包和大部分精灵状态来自玩家存档。服务端验证云上传格式、校验和及版本，但没有验证每笔战斗奖励、消费和捕获。校验和只能证明传输一致；客户端签名或加密也不能让玩家自报余额自动成为可信资产。

后台必须分开显示三类数据：

| 数据范围 | 展示名称及用途 | 能否作为准确经济账目 |
| --- | --- | --- |
| 已上传主线存档摘要 | 「主线金币最近快照」，带上传时间、覆盖率和来源标记 | 否；只能说明已采集存档声称的余额，不能覆盖未上传或离线玩家 |
| 服务端钱包和托管资产 | 「全服联机币」「商城点券」「托管精灵」 | 可以在明确服区、币种和纳入范围后准确对账；钱包尚需开发 |
| 未来服务端权威主线经济 | 「全服在线主线金币」 | 逐步接管产出、消费、转账与存档恢复后，才能提供可信统计 |

首期即可以提供主线金币分布与排行榜，但页面必须标为快照统计。客户端上报的战斗、捕获、徽章、游戏时长和本地收入同样显示来源，不能直接作为惩罚或发放可交易资产的唯一依据。

账号、角色、存档槽、自动存档和历史备份需要分清。同一个角色的多个存档不能重复计入总金币。建议引入服务器分配的稳定 `character_id`，以「服务器、账号、角色、当前认可版本」形成统计主键；它与当前地图外观用的 0～7 `character_id` 完全不同，接口应使用不同字段名，例如 `online_character_id`。

历史存档没有稳定角色标识时，先标记为待归并，由玩家确认和迁移规则建立关联。关联未完成的记录单列数量与金额，不直接加入角色去重后的总额；不能仅凭训练师名相同认定为同一角色。真正独立的角色分别统计，恢复旧备份不新增一份资产。

**3. 后台页面与日常使用**

推荐主导航为「总览、玩家、经济、资产、交易与商城、运营操作、风险告警、审计与系统」。首版只展示已有数据和可执行操作，依赖未来模块的页面显示明确的未接入状态。

| 页面 | 主要内容 | 可进行的操作 |
| --- | --- | --- |
| 全服总览 | 当前在线、新增账号、账号 DAU、金币与点券分布、今日产出/回收、未决指令和告警 | 切换日期、服区、环境；点击指标进入明细 |
| 玩家检索 | 用户名、昵称、好友码、账号 ID、角色 ID；在线/封禁/注册时间/资产区间筛选 | 查看详情、保存筛选、授权导出 |
| 玩家详情 | 账号、角色、云档、钱包、精灵、道具、交易、商城、处罚、管理备注和时间线 | 在相应权限下发起 GM 指令 |
| 经济分析 | 各币种总量、产出、回收、转账、手续费、财富分布和趋势 | 按来源、玩家、事件及业务单号追查 |
| 资产查询 | 精灵唯一编号、当前所有者、来源、交易锁、容器；道具库存；装扮权益 | 查询流转、冻结托管资产、发起合规补偿 |
| 交易与商城 | 挂牌、成交、订单、兑换码批次、领取状态和退款/冲正记录 | 调查异常、暂停新增业务、按原业务恢复 |
| 运营操作 | 定向补偿、批量活动发放、封禁禁言、市场开关 | 预览影响、按权限执行、查看任务结果 |
| 风险告警 | 异常余额增长、重复奖励、异常交易、资产重复、对账差异 | 标记调查、关联证据、采取限制措施 |
| 审计与系统 | 管理员、角色权限、操作日志、采集延迟、聚合状态和备份状态 | 查询审计、管理权限、重跑报表 |

玩家详情顶部固定显示账号标识、昵称、状态、最后活动时间、当前会话和风险标记。详情内的每个余额和资产均显示「服务端记录／存档快照／客户端上报」、数据版本和更新时间。未知值显示“未采集”，不能显示为 0。

玩家查询支持融合头部/身体、等级、闪光、IV、特性等项目特有维度。托管精灵可以按唯一资产 ID 查询；本地快照中的精灵在唯一身份和可信来源建立前，仅提供存档内检索和疑似重复提示。

典型使用流程：从总览发现当日金币产出突增 → 进入来源分布 → 筛选相关玩家 → 打开流水及奖励事件 → 核对证据 → 冻结有问题的经济操作 → 执行有记录的修复 → 查看对账结果。

**4. 统计口径与报表**

所有图表标明币种、服区、环境、时间范围、数据截止时间、统计版本及覆盖率。金额使用整数最小单位，不把联机币、主线金币、点券和人民币换算相加。测试环境与生产资产隔离；测试账号在业务层明确标记。活跃与经营分析可默认排除测试账号，但完整生产账本总额必须包含生产范围内的全部账户，另列测试及封禁账号占用；排除账户后的筛选结果标为子集，不能称为全服总额。

| 指标 | 建议定义 |
| --- | --- |
| 当前在线 | 有效游戏会话且世界心跳未超时的去重账号；有效登录 token 数另列，不能当在线人数 |
| 注册账号 / 新增账号 | 当前服务器注册账号总数 / 统计期内完成注册的账号数；旧临时身份另列 |
| 账号 DAU / WAU / MAU | 服务端收到有效游戏会话活动的去重账号；日活不能直接相加得到月活 |
| 留存 | 首次有效游戏活动所在日期为分组起点，计算 D1、D7、D30 再次活跃；统计接入前缺少历史的数据不追溯伪造 |
| 在线时长 | 根据会话及心跳计算有效区间，断线按超时封顶、同账号重叠区间取并集；区别于存档内游玩时长 |
| 全服货币存量 | 指定时点玩家持有的可用额、冻结额与托管待结算额，每份余额仅计一次 |
| 流通余额 / 冻结余额 | 可支出与受限金额分别展示；账本字段须统一为“可用与冻结分列”，不能重复加总 |
| 系统产出 | 战斗/任务等可信奖励、活动发放、补偿、新手发放、NPC 收购等新增进入玩家持有范围的金额，按来源拆分 |
| 系统回收 | NPC 消费、培养费用、市场手续费、管理员回收等离开玩家持有范围的金额，按销毁或系统保有拆分 |
| 玩家收支 | 玩家账本收入与支出，细分系统奖励、交易转入、交易转出、消费与手续费；不能用余额差反推总收入 |
| 玩家间成交额 | 已完成交易的成交金额；同一交易只计一次，不将买方和卖方流水各算一次 |
| 财富分布 | 人均、中位数、分位数、前 1%/10% 持有比例，附账号/角色分组口径 |
| 商品价格趋势 | 已成交样本的中位价、数量及样本量；挂牌价另画，融合与 IV 等差异明显的精灵分组统计 |
| 系统账户余额 | 手续费账户、活动账户等分别列示；系统收入不自动等于货币销毁 |

“收入”需要在界面上拆为以下含义：玩家游戏收入、系统回收金额、市场成交额、商城点券消费、真实支付收款。前四者都不是现金营业收入。

若以后接真实支付，再增加订单应付、支付成功、退款、拒付、渠道费、净收款、付费账号数、ARPU/ARPPU 等报表。按支付渠道核验结果与支付/退款事件时间统计；未接支付时显示“未接入”，兑换码和管理员发点券不算充值收款。不同法币分别报表，支付收款也不直接替代财务收入确认。

两类总量公式要分别使用：

- 玩家持有量期末 = 期初 + 系统发入玩家范围 − 玩家支付给系统或销毁的金额。玩家之间转账在全服范围相抵。
- 全部已发行且未销毁的货币 = 玩家持有 + 玩家托管待结算 + 系统保有，按账户分类互斥汇总。手续费进入系统账户时，只改变归属，不减少该口径的总量。

每笔交易的发行、回收、系统保有、补偿或冲正均有明确分类；统计范围迁移和历史期初导入也单独列示，不能被解释为当日正常玩法收入。

例如 A 向 B 购买 10,000 联机币的精灵，另付 200 手续费：成交额为 10,000；A 支出 10,200；B 收入 10,000；200 进入系统手续费账户。玩家持有量减少 200，全部未销毁货币总量不变。若规则明确将手续费销毁，后一个口径才减少 200。此例仅说明记账方式，不替换交易中心方案的收费规则。

首版提供今日/昨日/近 7 天/近 30 天/自定义区间、同比区间比较、来源排行榜和 CSV 导出。对于尚未采集的历史区间显示缺失，报表重算须可复现。

**5. 数据采集与技术结构**

建议结构为：Web 后台 → 管理 API → 玩家查询/报表查询与管理指令 → 现有游戏业务服务；游戏业务提交 → 持久事件 → 报表聚合。查询与写操作使用不同权限，统计不能成为玩家交易成功的外部前置条件。

前端建议 Vue 3 + TypeScript + Element Plus + ECharts；服务端管理能力继续用 Python。框架只是实现建议，可在正式开发前按团队维护能力替换。

首期继续使用现有 SQLite 事务体系。统计查询采用单独的只读连接、增量投影或一致性快照；后台写指令由现有持有实例锁的游戏服务执行。不能为了启动后台再实例化一个 `Store`：当前启动过程包含清理在线状态和恢复逻辑，第二个实例也会违反单实例约束。

报表聚合不要走当前每个游戏请求使用的 `BEGIN IMMEDIATE` 路径，不在游戏全局锁内解压所有云档或全表生成报表。读事务设置时限，避免长期阻碍 WAL 检查点；任务按批处理，显示采集积压和最近成功时间。数据规模或多实例需求超出单机能力时，再整体规划 PostgreSQL 迁移。

管理 API 使用独立 `/admin/v1` 路由与管理员认证。当前生产游戏入口只接受特定 `/v1` 路径且拒绝查询字符串，因此后台分页、筛选和权限需要专门的路由与代理规则，不能假设直接挂接口就能使用。

建议新增或复用以下业务模型：

| 数据模型 | 职责与约束 |
| --- | --- |
| 管理员、角色、权限、管理会话 | 与玩家凭据分开；服务端逐项校验权限 |
| 玩家状态、处罚、管理备注 | 记录作用域、原因、起止时间和执行人；备注不混入公开名片 |
| 角色注册表、槽位关联、玩家摘要 | 稳定角色 ID、当前认可版本、来源、更新时间、字段可信度和归并状态 |
| 活动事件、会话区间 | 注册、有效活动、上下线、处罚等服务端事实；支持账号去重和留存 |
| 钱包、账本交易与分录 | 与商城/交易中心共用一套；按币种平衡，余额及冻结额约束，系统账户明确分类 |
| 资产事件 | 资产 ID、来源事件、前后所有者、容器、业务单号；不复制出第二份资产 |
| 管理指令、审计日志 | 参数指纹、目标、预期版本、状态、结果、操作理由和变更摘要 |
| 持久事件待处理表、聚合游标、日/小时报表 | 与业务事务一并落事件；按唯一事件去重，增量重算及重启恢复 |

钱包采用商城和交易中心已规划的共享基础，不为后台新建第三种钱包。通用 `operations` 可继续协助短期请求恢复，但长期经济去重、账本和审计有独立保留策略。

存档查询采用服务端的只读、安全摘要提取器：校验格式和版本、限制压缩与解压大小、对象数和引用、只读取白名单字段，不实例化 Ruby 对象、不执行脚本。摘要必须关联原存档 revision、哈希和提取器版本。解析失败保留原档并提示错误，不阻断正常上传，不将缺失字段视为零。

摘要提取仅改善查询能力，不证明资产来源。只靠两次快照做差无法准确区分刷怪、消费、交易和回档，所以旧版本玩家的“收入来源”允许为空；接入埋点后的客户端事件也单列为上报数据。

建议新版本向服务端声明平台和版本作为诊断信息，旧客户端显示未知；不把现有匿名安装 ID 与账号强行关联。Matomo 保持现有匿名用途，安装活跃和账号活跃在后台分别命名、分别解释。

**6. GM 操作与执行规则**

| 操作类型 | 首期安排 | 关键限制 |
| --- | --- | --- |
| 查询、备注、工单关联 | 首版 | 敏感查询与导出留审计；默认隐藏凭据和完整 IP |
| 踢下线、禁言、封禁、解封 | 首版 | 服务端统一执行；禁言检查聊天入口，封禁检查认证及已有会话 |
| 冻结交易、冻结钱包支出或托管资产 | 随对应经济模块接入 | 区分资产冻结和账号封禁，明确是否允许入账、领取与恢复 |
| 发放/扣回联机币和点券 | 钱包阶段 | 整数增量、业务原因、幂等 ID、余额限制、账本与审计同事务 |
| 发放/回收托管精灵、道具和权益 | 资产模块接入后 | 受信任目录、当前所有权、占用锁和已消耗状态检查 |
| 撤销异常挂牌、暂停购买或新增交易 | 市场/商城接入后 | 保留历史及恢复查询；取消、退款和解锁按业务状态机处理 |
| 主线存档金币/道具修复、卡图处理 | 独立后续阶段 | 受控维护会话、版本比较、安全字段修复与客户端重新载入 |
| 整档回滚、批量发放、大额冲正 | 高权限后续能力 | 影响预览、额度控制、复核与恢复演练；不能绕过账本和资产归属 |

后台不提供任意 SQL、执行脚本或无约束编辑存档对象的入口。界面可以展示“调整到指定余额”，实际仍需计算基于预期版本的差额，走完整增减流水。

每次管理操作遵循：选择目标 → 填写原因及业务编号 → 查看当前版本和变更预览 → 确认 → 服务端重新校验 → 提交 → 返回指令编号 → 查询最终结果。超时显示“结果确认中”，使用同一指令编号重查或重试；同编号不同参数拒绝执行。

需要复核的操作记录待复核状态、复核人和失效时间；执行前再次检查版本、余额和资产归属，数据变化后重新预览。普通查询和备注不要求双人复核；大额、批量、整档回滚和权限提升按可配置阈值启用。

踢下线与封禁不能只删除 `world_presence`。需要撤销游戏会话、处理云租约，在云上传、地图、聊天、交易等认证入口统一检查状态，并确保旧 token 不能继续写入。封禁不得自动删除资产；正在进行的交易依照状态机完成或撤销。客户端保留未同步进度的恢复记录。

主线存档修复不能直接覆盖正在游玩的存档。后续流程应先维护冻结并通知客户端，在安全点停止写入；对未响应设备撤销旧租约，阻止旧分片及在途提交；记录预期 revision，创建一致性备份，执行白名单变更并增加版本；玩家重新拉取后才能继续。不可安全保存的本机进度单独保留待恢复，不承诺强制断线绝不丢未上传进度。

整档回滚不得恢复已转出的精灵或把旧余额重新导入服务端钱包。要先检查该版本之后的经济关联，必要时只恢复非经济进度，并以补偿事务处理资产差异。新版本客户端必须尊重服务器维护代次，旧上传回执只能作为历史结果查询，不能重新激活旧存档。

**7. 全服经济账本与主线接管路径**

要最终实现 PokeMMO 风格的可靠全服金币和收入查询，需要统一资产入口，而不是只给金币字段增加上传埋点。

建议按以下顺序推进：

1. 建立共享钱包、账本、系统发行/回收账户、长期幂等记录与对账；先服务于联机币和商城点券。
2. 市场购买、面对面转账、手续费、补偿等都通过钱包业务提交，资产转移、订单、分录和事件同事务成功。
3. 主线在线角色建立稳定身份、经济版本和唯一资产编号。金币及可交易背包由服务端裁定，客户端只提交操作意图并显示结果。
4. 逐类接管战斗奖励、任务奖励、NPC 买卖、培养/融合/孵蛋费用、掉落、捕获、邮件、活动与所有其他经济入口；没有可信校验的来源保持隔离，不能凭客户端声称胜利就发币。
5. 回档、换槽、跨设备、导入/导出、调试与 Mods 修改不能回灌在线经济。离线玩法可继续存在，但它与在线资产的导入规则独立。

现有联机战斗仍由客户端/房主引擎结算；要把相关奖励列为可信产出，需要增加服务端可验证的战斗/奖励条件，或把奖励限制在能够服务端验证的活动内。这部分属于主线在线经济改造，工作范围明显大于后台页面。

历史主线余额不自动按 1:1 导入联机钱包。迁移建议保留历史主线玩法，把已核验的新在线资产纳入权威经济；如确需迁移历史资产，应确定截止版本、准入条件、一次性导入额度和来源标记，记为期初迁移，不记为当天正常产出。

对账按币种至少核对：分录合计平衡、钱包等于期初加累计分录、冻结额与业务占用一致、资产所有者唯一、订单交付与扣款对应、玩家总额与系统账户的归属变动一致。发现差异进入告警与调查，修复采用冲正或补偿，不删除原流水。

**8. 权限、审计和风险告警**

| 建议角色 | 默认权限 |
| --- | --- |
| 数据观察员 | 聚合报表、脱敏玩家摘要，无修改权限 |
| 客服 / GM | 授权范围内的玩家详情、备注、禁言及有限处罚 |
| 运营 | 活动、目录、兑换码及额度内补偿 |
| 经济管理员 | 钱包、账本、对账及受控冲正 |
| 系统管理员 | 管理员与权限配置、基础服务；高额经济操作仍按复核策略执行 |

管理员采用独立账号、会话与二次验证；密码与 token 不在查询结果、日志或导出中返回。权限在服务端检查，区分查看、导出、发放、扣回、冻结和复核；界面隐藏按钮不构成授权控制。后台使用 HTTPS，设置合理会话期限和登录限制，按部署需求增加访问网络限制。

审计至少记录操作者、权限角色、目标账号/角色/资产、动作、原因、业务编号、预期与实际版本、前后差异、时间、请求与结果。业务变更、审计和执行回执在同一事务落库，失败也留下不含秘密的尝试记录。日志可搜索和导出，普通管理员不能编辑或删除。

审计建议追加写入并周期性归档到独立受限备份；需要更强的防篡改能力时增加外部签名或校验链。仅在同一数据库禁止 UPDATE，不能保证数据库运维人员也无法修改。

首期优先检测重复业务事件、钱包对账差异、负数/越界金额、重复资产归属、异常补偿频次与数据采集中断。随后加入单位时间收入异常、循环转账、偏离同类资产成交价格、新账号资金集中等规则。阈值按规则版本保存，并区分可信账本异常和存档快照异常。

IP 共用、异常高价和主线余额突增只能作为调查线索，默认不自动封号。每条告警提供原始事件、规则、时间范围及关联流水；IP/设备详情按职责授权并设置保留期限，不额外收集硬件唯一标识。

**9. 首版接口边界**

以下为职责示意，不是现有可调用接口，也不要求首期一次实现全部端点：

| 接口组 | 用途 |
| --- | --- |
| 管理登录、退出、当前权限 | 独立管理会话与二次验证 |
| `GET /admin/v1/overview` | 指标、口径、数据截止时间及采集状态 |
| `GET /admin/v1/players`、玩家详情 | 分页检索、账号/角色/存档摘要 |
| 玩家会话、资产、账本、处罚、时间线 | 以稳定业务 ID 跳转关联证据 |
| 经济汇总、来源分布、排行榜与对账 | 按币种、服区、环境、时间与来源筛选 |
| `POST /admin/v1/commands` | 提交受支持的类型化管理指令，带指令 ID 和预期版本 |
| 指令详情、复核与结果查询 | 处理待复核、执行中、成功、失败及冲突 |
| 报表导出任务 | 按固定快照异步生成，记录筛选条件、口径与权限 |
| 审计、告警、采集状态 | 调查与运行监控 |

搜索和导出限制时间范围及每页数量，使用稳定排序和游标，防止一次扫描全部私有存档。导出结果复核授权后下载、设置过期时间，对 CSV 文本进行公式注入防护；不能提供自定义 SQL 查询入口。

**10. 实施分期与验收门槛**

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| A：查询与账号管理首版 | 管理员权限、总览、玩家检索详情、在线会话、存档摘要、托管资产、备注、踢线/禁言/封禁和审计 | 不依赖商城上线即可使用；快照与可信数据区分；封禁后旧会话无法继续操作 |
| B：共享钱包与经济后台 | 与商城/交易中心共用钱包及账本、总额/产出/回收/成交报表、补偿与扣回、对账与风险告警 | 精确到已接入的币种和资产；重试、并发、重启不重复扣款或发放 |
| C：主线在线经济接管 | 稳定角色和资产 ID、奖励/消费验证、唯一资产、存档与钱包分工、受控主线修复 | 能可靠统计在线主线金币；旧存档、离线导入与回档不能复制资产 |
| D：运营增强 | 留存分群、更多风险规则、批量活动复核、进阶价格报表、真实支付对账（如接入） | 历史可重算、权限可验证、批量任务可恢复、支付来源可核验 |

建议先交付 A，随后把 B 与商城、交易中心的钱包基础一起设计和实施。A 可以完成“查人、看存档、看在线、处理账号”；B 完成“查账、统计可信货币、操作托管资产”；C 才能覆盖全部在线主线金币的准确账目。不能以后台图表完成为由，宣称主线经济接管完成。

首版暂缓任意主线存档在线编辑、未经核验的历史资产入账、自动封禁、跨服资产调拨和真实支付。这些功能需要各自的数据与状态机基础，后台模型预留关联即可。

详细验收至少包含以下场景：

- 同一角色的手动槽、自动槽与备份不重复计入总金币；未归并、离线、过期和解析失败的数据在覆盖率中明确显示。
- 同账号跨设备按账号去重活跃；登录有效但没有游戏心跳的 token 不计当前在线；跨日、断线和重启统计合理。
- 玩家交易不虚增货币产出或成交额；手续费保有与销毁分别核算；可用、冻结、待结算不重复加总。
- 修改钱包时同步发生消费、转账或 GM 操作，只允许满足预期版本和余额约束的提交；响应丢失后查到唯一结果。
- 普通玩家 token 不能访问后台；只读管理员不能修改；经济管理员不能绕过配置的复核策略。
- 踢线、封禁、冻结与在途云分片/交易并发时状态一致；旧会话不能绕过，资产锁不会永久遗留。
- 存档摘要遇到损坏压缩、超限对象或未知版本时安全失败，游戏服务保持可用；失败不被统计为零余额。
- 备份恢复包含钱包、订单、资产、账本、经济去重记录、指令和审计的一致性单元；统计投影可重建，已执行指令不会重放。
- 原始业务与聚合报表按相同快照能对账；显示数据延迟；报表/导出任务不会长时间占用游戏请求锁。
- Windows 与 Android 在管理操作后均能正确暂停、提示和恢复；服务端测试通过不能代替游戏内验收。

性能验收基于明确的目标在线人数、账号数、存档体积和流水量建立数据集；记录后台查询和报表运行时游戏接口的延迟与吞吐。具体容量和耗时目标在开发前确定，不凭 SQLite 或前端框架名称承诺承载量。

本方案描述目标范围，不表示表中每项均已完成。实际功能及验证结果以[后台使用与开发验收](multiplayer-admin-operations.zh-CN.md)和其中的阶段进度为准。
