**KIF 在线商城模块方案（讨论稿）**

日期：2026-10-22。范围：需求、交互、经济规则、技术边界、分期与验收；本次不实现代码。

建议把新模块定位为「PokeMMO Gift Shop 风格的官方商城」：在线账号拥有独立点券钱包，购买装扮并即时试穿，购买记录和拥有权跨设备恢复，同地图玩家能够看到已装备外观。玩家寄售市场作为独立后续阶段。

以下采用三个规划默认值：首版不接真实支付；商品以账号绑定的永久外观为主；本地主线金钱不兑换商城点券。这些是本方案的建议，不是已经确认的产品要求。

**1. 参考对象与项目现状**

PokeMMO 参考的是商城使用体验：游戏内入口、专用 Reward Points、分类浏览、外观商品，以及购买后在游戏中使用。其官方支持说明了 RP 与支付渠道的关系；本项目首版仅借鉴独立点券的产品结构，不照搬充值渠道和价格。[PokeMMO 官方 RP 说明](https://support.pokemmo.com/knowledgebase/article/reward-points-not-received)。

本次实际阅读了本机 `D:/others/OpenMMO`，并核对上游源码：

| 参考文件 | 已观察到的能力 | 本项目如何借鉴 |
| --- | --- | --- |
| [GameShopCatalogPacket.kt](https://github.com/openmmo-org/OpenMMO/blob/master/protocols.game/src/main/kotlin/de/fiereu/openmmo/net/game/packets/GameShopCatalogPacket.kt) | 商城目录携带 points，商品包含标识、分类和 cost 等字段 | 由服务端提供版本化商品目录和余额；商品用稳定标识引用 |
| [CurrencyBalancePacket.kt](https://github.com/openmmo-org/OpenMMO/blob/master/protocols.game/src/main/kotlin/de/fiereu/openmmo/net/game/packets/CurrencyBalancePacket.kt) | 定义了两个余额字段 | 把余额同步作为独立能力；字段本身不能证明完整的双货币经济已经实现 |
| [ShopService.kt](https://github.com/openmmo-org/OpenMMO/blob/master/server.game/src/main/kotlin/de/fiereu/openmmo/server/game/services/ShopService.kt) | NPC 货架、购买数量、余额、出售持有量及离开地图后的商店有效性检查 | 商品、价格、数量与购买资格由服务端裁定 |

`ShopService.kt` 的买卖使用分步修改和失败补偿；本方案对商城余额、订单和权益采用同一数据库事务。此次查看未发现可直接复用的完整付费商城业务，不能把协议定义当作充值、订单、退款已经完成的证据。OpenMMO 上游 README 已标为归档，本项目继续沿用 Ruby/Python 的现有结构，独立设计接口。[OpenMMO README](https://github.com/openmmo-org/OpenMMO)。

当前 KIF 已具备以下基础：

| 已有能力 | 对商城的影响 |
| --- | --- |
| 注册登录、账号身份、在线会话和按账号隔离的云存档 | 复用登录；钱包和商品拥有权绑定服务器上的身份 |
| `service.py` 的 SQLite 写事务、operations 请求日志及回执查询 | 复用事务与请求去重机制，补充长期保存的商城业务记录 |
| 服装、帽子、发型目录，换装菜单及 `TrainerClothesPreview` | 复用资源格式和绘制能力，新增商城页面及安全的试穿草稿 |
| 联机名片、六槽精灵展示 | 后续扩展边框、称号等展示权益，不把现有功能改成收费解锁 |
| 服务器托管收藏箱、资产锁及托管交换 | 为后续寄售提供资产所有权基础；当前不是通用商品背包 |
| 异步联机请求和 Android 网络桥接 | 商城网络请求按帧处理，适配键盘及触屏 |

需要补齐的基础：商城钱包、目录、订单、装扮权益、装备校验、管理操作，以及地图外观同步。目前地图只同步 0～7 的预设 `character_id`，不会自动展示玩家购买的分层服装。

现状依据：`docs/multiplayer-online-world.zh-CN.md`、`server/multiplayer/README.zh-CN.md`、`Data/Scripts/054_Multiplayer/`、`Data/Scripts/050_Outfits/`。

**2. 功能定位与范围**

| 模块 | 定位 | 本轮方案中的安排 |
| --- | --- | --- |
| 在线商城 | 官方出售装扮和服务权益 | 首版主体，新设独立入口 |
| 原有 NPC 商店、服装店、Kuray Shop | 使用原有存档和游戏金钱的本地玩法 | 保持原有规则；商城增加专属商品 |
| 玩家交易所（GTL 类） | 玩家上架资产，其他玩家购买 | 后续独立模块，先完成可信资产和货币来源 |

首版完整闭环为：登录账号 → 打开商城 → 浏览和试穿 → 确认价格 → 购买 → 权益入账 → 装备 → 他人可见 → 跨设备恢复。

首版包含商品分类、分页、详情、余额、点券获取说明、试穿、购买、我的装扮、装备管理、订单与余额明细、限购、上下架和异常恢复。兑换码作为首版可实际使用的点券来源；管理员发放用于测试、活动奖励和补偿。

首版建议暂缓：真实支付、赠送、点券券交易、抽奖箱、能力数值商品、限时增益、普通背包消耗品、精灵售卖和玩家寄售。所有暂缓能力不展示可点击的空入口。

**3. 页面和操作体验**

入口放在在线模式暂停菜单的「商城」，联机大厅保留同名快捷入口。离线模式不进入购买流程；旧 NPC 商店继续正常使用。进入商城不要求玩家先进入联机房间。

页面采用适合现有游戏窗口的紧凑布局：顶部显示商城名称和点券余额，左侧或顶部是分类，中间为商品列表，选中商品后打开详情和较大的角色预览。较窄窗口用列表页和详情页切换，避免在手机屏幕里挤入三栏。

首版分类为「推荐、服装、帽子、发型、我的」。名片装饰准备好后增加对应分类；背饰、坐骑等依赖新外观槽位的商品另行扩展。推荐页直接展示精选商品，不依赖大幅广告资源。

商品卡片显示名称、缩略图、价格和「已拥有／限时／限购」等必要状态。详情必须明确商品效果、永久或期限、账号共享范围、绑定规则、资源是否兼容，以及活动结束时间。限时上架与限时使用使用不同文案。

详情提供「试穿」和「购买」。试穿支持四方向查看；已准备的行走帧可播放。退出试穿恢复原外观，购买不自动替换正在穿戴的服装，购买成功后可选择「立即装备」。支持连贯试穿帽子、服装和发型组合。

确认购买时显示商品、数量、单价、总价和购买后余额。永久装扮数量固定为一，已拥有时显示「已拥有」，不能再次扣费。目录或价格变化时要求重新确认，不使用新价格静默成交。

「我的」集中提供已购装扮、当前装备、订单、点券明细和兑换码。订单显示成功、处理中或失败原因；请求超时且结果未知时显示「正在确认购买结果」，暂时禁止重复提交同一购买意图。

键盘操作延续方向键、确认和取消；鼠标及触屏提供明确按钮和滚动区域。网络等待期间保留界面绘制与取消操作，按下取消只退出等待界面，不能把已经提交成功的交易当作撤销。

**4. 商品与经济设计**

| 资产或货币 | 归属及权威来源 | 建议用途 |
| --- | --- | --- |
| 主线金钱 | 现有本地角色存档 | NPC 商店、Kuray Shop 等现有消费 |
| 商城点券（暂名 RP） | 当前服务器、当前账号的服务端钱包 | 首版装扮购买；不转账，不兑换主线金钱 |
| 活动代币 | 后续由服务端独立记录 | 特定活动兑换；首版无需先增加第二个可消费币种 |
| 已购装扮权益 | 服务端账号记录 | 同账号不同在线存档共享拥有权，装备组合可不同 |

点券首版通过服务器验证的兑换码、管理员有记录的奖励与补偿获得。兑换码应记录批次、有效期、发放量及每账号使用上限；个人码只能由指定账号使用。使用服务器时间判断期限，并限制暴力尝试。

现有联机战斗由房主引擎结算，主线进度和背包也不由服务器验证。因此不直接用客户端声称的通关、胜场、在线时长或本地金钱增加可转让价值。未来增加活动奖励时，先明确服务端可验证的领取条件与账号刷取边界。

商品优先顺序如下：

| 优先级 | 商品类型 | 发放方式及限制 |
| --- | --- | --- |
| 首版 | 专属服装、帽子、发型 | 购买即写入账号永久权益；绑定账号，不支持出售 |
| 第二阶段 | 名片边框、称号、配色组合 | 新增对应展示字段和渲染，服务端校验拥有权 |
| 第二阶段以后 | 已拥有商品组成的套装、节日商品 | 对套装内容逐项去重；活动到期下架但已购权益保留 |
| 独立评估 | 改名、容量、便利服务 | 先明确账号或角色作用域、当前免费能力和使用次数 |
| 独立评估 | 背饰、坐骑等新外观槽位 | 必须具备完整素材、动作与远端同步支持后再上架 |

以下仅为内部测试定价示例，商品名称是设计示意，素材尚未确认；不是 PokeMMO 价格，也不代表人民币换算：

| 示例商品 | 测试点券 | 规则 |
| --- | --- | --- |
| 融合研究员服装 | 300 | 永久、账号绑定、限购一次 |
| 探险帽 | 100 | 永久、账号绑定、限购一次 |
| 研究员发型 | 100 | 永久、账号绑定、限购一次 |
| 节日限定服装 | 400 | 限时上架、永久使用、账号绑定 |

首发建议控制在约 12～20 件经过资源与动作验证的商品，实际数量服从素材审查。先用少量测试点券跑通浏览、购买和换装，再根据活动产出量调整价格。

已经免费提供的服装和功能继续保留。不能直接把现有无限 PC 扩展、菜单便利功能或自由调节的单机参数重新包装成付费权益。商城 SKU 必须映射到明确的专属资源或新增服务；已有本地解锁列表不能反向证明玩家买过商城商品。

**5. 账号、云存档与外观同步**

钱包、订单和拥有权的作用域统一为「服务器 + 认证身份」。相同账号在 Windows、Android 和不同在线存档下读取同一份权益；更换服务器后使用该服务器自己的钱包。现有匿名休闲身份不自动获得商城购买权限，首版要求注册登录的在线账号。

商城余额和拥有权不从云存档恢复，也不接受上传存档覆盖。云端存档仍负责主线角色；商城数据库负责经济记录。回滚存档不会返还已消费点券，也不会撤销已购买外观。

同账号所有在线存档共享购买资格。每份存档可以保存各自选择的装备组合，但在线登录及加载完成后必须重新用服务端权益校验；选装数据只是偏好，不是拥有权证据。首版借用当前有效的在线写入会话提交购买和装备，保留现有单账号单写入设备规则。

本地已有服装和商城服装分别记录来源，UI 可合并展示。不能为同步商城权益直接覆盖原有 `unlocked_clothes`、`unlocked_hats` 等列表，也不能将本地列表全部上传认证为商城资产。

购买权益先在服务器持久化，客户端再刷新「我的装扮」。不需要等待一次云存档上传成功才算购买完成。客户端崩溃或换设备后从服务器重新读取即可，不走「再次向背包补发一件」的路径。

地图外观同步是首版的必要内容：定义版本化外观描述，包含受支持的基础角色、服装、帽子、发型、颜色和外观修订号。服务端验证可用资源及商城权益，公开广播经过校验的外观投影；不广播账号完整购买清单。

普通免费外观使用受信任的基础资源目录；商城专属标识必须有对应权益。客户端只根据允许的资源 ID 查找安装素材，服务端不发送任意路径或脚本。外观资源缺失时用默认角色显示，明确提示更新；尚不支持该资源版本的客户端不得购买或装备对应商品。

远端角色需按自己的外观描述生成位图，不能读取本机 `$Trainer` 的衣服。按外观版本缓存合成结果、按需更新，不在每次坐标同步时重新合图。步行、跑步、骑行、冲浪等状态的远端展示按现有同步能力逐步补齐；首版未支持的状态使用明确的基础外观回退并纳入素材验收。

还有一个项目特有问题：现有服装商店的试穿适配器会临时修改 `$Trainer.clothes`。新商城应使用独立预览草稿；浏览过程不修改真实角色、云存档或正在广播的外观，避免未购买衣服因自动保存或地图同步提前生效。

**6. 购买、事务与故障恢复**

建议流程如下：

1. 客户端取得商品目录版本、余额和账号权益，展示服务端价格。
2. 玩家确认后，先在本地日志保存本次购买意图和固定 `request_id`，绑定当前服务器和身份。
3. 提交商品 ID、数量、目录／报价版本及预期总价；这些是购买意图，服务器独立重算价格和资格。
4. 在同一 SQLite 写事务中检查登录会话、商品有效性、兼容资源、期限、限购、重复拥有和余额。
5. 一次提交完成扣款、钱包流水、订单、权益发放和请求回执；任一失败则全部回滚。
6. 客户端显示订单结果并刷新权益与余额，玩家可立即装备。
7. 响应丢失时查询原请求或原订单；仍需重试时使用完全相同的请求编号与内容。

`request_id` 只解决一次请求的重放，还需要业务唯一约束：同一账号对同一永久权益只有一份有效拥有权；同一订单只扣款一次；同一来源奖励只入账一次。不同请求编号也不能绕过永久商品重复购买和限购。

价格采用整数点券，禁止浮点金额；数量、单价、总额和余额设置明确上下限并检查乘法溢出。限量库存、个人额度和活动时段都在提交事务内再次判断。首版优先使用不限总库存的永久商品，减少全服抢购需求。

| 异常情形 | 预期处理 |
| --- | --- |
| 扣款前校验失败 | 不扣款、不创建权益，显示具体原因 |
| 事务提交前进程终止 | 数据库回滚，重试可继续 |
| 已提交但回包丢失／客户端退出 | 原订单保持成功，查询后恢复显示，不再次扣款 |
| 两个请求同时购买同一永久外观 | 只成功一份，余额只扣一次 |
| 目录更新、涨价、下架或限购变化 | 重新确认或拒绝；已经成交的订单按当时快照保留 |
| 购买后恢复旧云存档 | 登录重新获取权益与余额，不重新发放、不退回点券 |
| 本机资源缺失 | 已有权益保留，装备回退并提示更新；购买前尽量拦截 |
| 切账号、退出或会话到期 | 待处理操作保留在原身份下；恢复认证后查询，不能转到新账号提交 |

订单、流水和经济去重记录需要长期保留，不能只依赖可能清理的通用 operations 日志。数据库备份和恢复必须将钱包、订单、权益、流水及去重记录作为同一一致性单元；不得仅恢复余额表。

**7. 模块划分和接口草案**

客户端新增商城业务客户端、商城页面、试穿草稿与权益投影层，复用已有认证、异步网络、本地请求日志和中文字体作用域。只读缓存提高打开速度，余额、价格与拥有权最终仍以服务器返回为准。

服务端增加商城业务模块，挂入现有 Store 与路由体系，沿用当前 SQLite 事务，不在首版另建微服务。商品内容使用受信任、带版本的配置；余额、订单、限购、库存和权益放数据库，不能在 JSON 配置中保存玩家余额。

下列接口仅用于说明职责，名称可在实现时按现有路由规范调整：

| 接口职责 | 建议入口 | 关键语义 |
| --- | --- | --- |
| 浏览目录 | GET `/v1/shop/catalog` | 分类、分页、目录版本、商品可见性和兼容要求 |
| 查看钱包 | GET `/v1/shop/wallet` | 当前账号余额与余额版本 |
| 查看权益 | GET `/v1/shop/entitlements` | 当前账号拥有的商城资源 |
| 购买 | POST `/v1/shop/orders` | 商品、数量、版本、预期金额、固定请求编号 |
| 查询订单 | GET `/v1/shop/orders`、`/{id}` | 仅本账号可读；分页查询 |
| 查看流水 | GET `/v1/shop/ledger` | 点券来源和去向，不暴露其他账号 |
| 兑换点券码 | POST `/v1/shop/redeem` | 服务端核验、原子入账、按账号及批次去重 |
| 装备 | POST `/v1/shop/equipment` | 校验权益和资源，返回可广播的外观描述 |

购买接口不接受客户端指定扣款账号、任意商品效果、可执行脚本或本地背包快照。鉴权统一取服务端身份，商城的 POST 不加入现有「无需经济操作日志」的瞬时请求例外。

建议的数据职责：

| 记录 | 最低需要保留的信息 |
| --- | --- |
| 商品目录／商品版本 | SKU、资源或权益 ID、分类、价格、币种、期限、限购、兼容版本、发放方式 |
| 钱包 | 账号、币种、整数余额、修订号 |
| 流水 | 唯一编号、来源事件、账号、增减数量、订单／奖励关联、时间 |
| 订单 | 账号、固定请求编号、商品及价格快照、金额、状态、时间、发放结果 |
| 权益 | 账号、权益键、来源订单、获得时间、有效期／撤销状态 |
| 兑换码／领取记录 | 安全摘要、批次、额度、期限、适用账号、唯一领取事件 |
| 外观投影 | 当前已验证的装备、资源版本及修订号 |
| 管理审计 | 操作者、动作、原因、关联订单／账号、变更前后信息 |

未来退款或补偿采用新增冲正记录，不删除原订单和原流水。首版账号绑定外观如需人工退款，应在同一事务中退点券、撤销对应权益并处理当前装备；涉及套装或其他来源重复权益时，需要先定义可撤销范围。

**8. 运营能力与真实支付的后续边界**

首版管理能力包含：发布／下架商品、设置起止时间和限购、暂停购买、发放或冲正测试点券、创建兑换码、查询订单、按订单恢复展示结果及查看审计。先提供受权限保护的管理工具，完整网页后台可后续建设；管理接口不暴露给普通游戏客户端。

商品可以按账号名单灰度开放，独立关闭购买和装备功能。紧急下架只阻止新购买，不直接删除已购权益；出现素材问题时可以停用展示并给出恢复或补偿安排。

未来接真实支付时，补齐支付订单、服务端回调验证、金额与币种核对、渠道事件去重、对账和退款／拒付状态。客户端返回「支付成功」不能直接加点券。支付模块是后续独立工作，不因设置了 RP 钱包就视为已经具备充值能力。

建议观察购买成功率、明确失败原因、未决请求恢复时间、余额与流水对账差异及资源缺失情况。日志不记录密码、登录令牌、完整兑换码或支付秘密。

**9. 玩家交易所如何承接**

如果「商城」后续还要包含 PokeMMO GTL 类的玩家买卖，建议新设「交易所」入口，区分官方售卖与玩家寄售。首版绑定装扮不因交易所上线自动变为可交易资产。

初期只考虑服务器托管资产，沿用收藏箱现有所有权与资产锁；本地休闲精灵、云存档导入精灵和本地背包不能直接上架。普通已购永久权益也不能直接当作库存物品，若将来要出售装扮券，需要独立的服务器物品实例模型。

交易所至少需要浏览筛选、挂牌、一口价购买、撤单、到期、我的挂牌和历史。上架先锁资产，购买在同一事务中扣买家余额、增加卖家余额、转移资产所有权、写入费用与回执；撤单和购买竞争时只能有一个结果。列表分页和排序不允许把待售精灵的私人字段全部公开。

进入这一阶段前必须决定交易货币及可信产出来源。可以另建服务端游戏币，但不能直接把本地 `$Trainer.money` 上报充值到交易钱包。仅仅把主线存档传到云端，也不能证明其中货币和精灵来源可信。

服务器托管收藏资产与主线队伍继续保留现有边界。让商城或交易所购买的精灵直接进入主线、再带道具回流，会形成新的跨区经济通道，需要独立设计。

**10. 分期交付**

| 阶段 | 交付内容 | 完成门槛 |
| --- | --- | --- |
| A：范围与资源确认 | 确认本方案默认值，清点首批 SKU、专属资源和动作；确定点券来源与购买归属 | 每件商品有明确效果、来源、预览和兼容要求 |
| B：商城首版 | 钱包、兑换码、目录、详情、试穿、购买、永久权益、我的装扮、订单恢复、装备和地图外观同步、基本管理 | 完整购买与展示闭环通过，断线／重启不多扣不丢权益 |
| C：展示与活动 | 名片装饰、称号、节日上架、套装去重和较完整运营管理 | 活动时间、组合拥有权与展示兼容验证完成 |
| D：独立扩展 | 按产品选择推进真实支付或服务器托管交易所 | 支付对账或交易经济边界先设计清楚，再单独实施 |

首版优先把「买得到、穿得上、别人看得到、换设备还在」完整交付。背饰新槽位、精灵售卖、主线消耗品、便利道具和数值加成不挤进 B 阶段。

普通背包道具需要特别说明：服务器扣款与本地存档写背包不是同一事务，服务器回执加客户端 ack 也无法阻止玩家恢复旧备份复制消耗品。后续若要加入，应选择明确的休闲发放边界或服务器权威背包，而不能宣称现有回执机制已解决防复制。

**11. 验收标准**

| 维度 | 必须验证的结果 |
| --- | --- |
| 正常购买 | 点券减少、订单和权益同步增加；同账号跨存档、跨设备一致 |
| 业务约束 | 余额不足、非正数、越界金额、过期、下架、资源不兼容和重复拥有均不能错误扣款 |
| 重复与并发 | 连点、同编号重发、不同编号重复购买、兑换码重放和库存竞争只产生合法结果 |
| 故障恢复 | 提交前崩溃回滚；提交后丢包、客户端退出及服务重启后能找回唯一订单 |
| 云存档回滚 | 恢复购买前存档，余额和权益仍正确；本地列表不能伪造服务器购买 |
| 试穿 | 未购买不装备、不自动保存、不广播；取消后原外观与染色保持正确 |
| 他人可见 | 两个独立账号实机验证穿戴、切图和重新登录；缺资源有受控回退 |
| 权限 | 不能查看他人钱包、订单或兑换记录，不能伪造商城装备或调用管理操作 |
| 客户端体验 | Windows 原生游戏与 Android 触屏实际走通；慢网时持续绘图和响应输入 |
| 资源和性能 | 首批商品逐个验证可用状态、方向和缺失回退；多人同图不重复无节制合图 |
| 对账与运维 | 钱包变动可追溯到流水；订单、权益、限购和备份恢复保持一致 |
| 原有玩法 | 离线存档、NPC 商店、Kuray Shop、旧服装解锁和联机功能保持兼容 |

服务端自动测试通过只是其中一项。最终应补充两个游戏进程、Windows 与 Android、真实断网与重启的端到端验证，保留失败记录和验收证据。本次只形成方案，没有执行上述开发或验收。

**12. 建议采用的产品决策**

建议首版确定为：官方装扮商城；使用账号级服务端 RP；通过兑换码和有记录的奖励发放测试点券；购买永久且账号绑定的服装、帽子、发型；同账号在线存档共享；包含试穿、订单恢复和同地图外观展示。

真实支付、玩家寄售、可交易点券券和对战收益商品分别留到后续决策。实现前最需要确定的是首发素材清单，以及是否接受上述首版点券获取方式。
